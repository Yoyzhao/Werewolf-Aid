## 2. 项目概述

### 2.1 背景与问题

狼人杀是强流程、强信息的社交推理游戏，线下组局存在三个典型痛点：

1. **主持门槛高**：面杀需要一位懂规则、能记住夜间顺序、会判定胜负的“上帝”。新手不会主持，导致组局困难。
2. **规则记忆负担**：板子、角色技能、行动顺序、冲突判定（如同守同救）容易记错，争议频发。
3. **玩家缺乏私人辅助**：玩家需在不暴露身份的前提下查看技能提示、记录场上信息、获得策略提示；线下又难以把这些信息汇总给每个玩家。

### 2.2 产品定位

面向**线下狼人杀场景**的微信小程序：用一台手机即可让**完全不会玩的人**按引导主持完整对局并自动给出结果；每位玩家可在自己手机上记录身份、标签与发言要点，获得 AI 整理建议，且**只看到自己该看的信息**。

v1.2 定位：**零门槛主持人（P0）+ 私人对局助手（P0）**；**配对码联机为 P1 可选增强**，不阻塞单机主持。

### 2.3 目标用户

| 用户 | 特征 | 核心诉求 | 优先级 |
| --- | --- | --- | --- |
| **新手主持人** | 不会玩狼人杀，被推举主持 | 一步步照做完成整局，不判断、不记忆、不出错 | P0 |
| **独立玩家** | 只想自己记录，不加入房间 | 标记身份、记标签/发言，数据留本机 | P0 |
| **进阶玩家** | 追求策略提升 | 用标签/发言要点沉淀信息，让 AI 帮忙整理 | P0 |
| **联机玩家** | 每人一部手机，线下同桌 | 配对即加入，自动拿到身份与公开进度 | P1 |

### 2.4 核心价值

- **零门槛主持**：把“懂规则”转化为“照着点”，主持人无需先验知识。
- **本地优先、断网可玩**：P0 全部主持流程与个人记录在本机完成；网络只用于 AI（可选）与 P1 联机。
- **自动裁定**：胜负、冲突、平票由系统判定，减少争议。
- **信息沉淀 + AI 整理**：标签与发言要点成为 AI 上下文；AI 输出“整理/可疑/建议/依据”，不冒充结论。
- **可选联机协同**：P1 提供配对码加入、阶段快照同步、按角色过滤视图；不加入也能玩。

### 2.5 成功指标

| 指标 | 统计口径 | 目标值 | 观察方式 |
| --- | --- | --- | --- |
| 新手主持完成率 | 首次使用的主持人完成一整局（进入结算）的比例 | ≥ 80% | 5–10 名新手实测 |
| 对局流程完成率 | 开局后进入结算的比例 | ≥ 90% | 实测记录 |
| 开局设置耗时 | 从进入主持到发牌完成 | ≤ 3 分钟 | 实测计时 |
| 规则判定错误 | 同守同救、限一瓶、连守、1.5 票、平票等用例 | 0 错误 | 规则测试用例 |
| AI 请求成功率 | 有效 Key 下返回三段以上内容的比例 | ≥ 90% | 云函数日志（脱敏） |
| P1 配对成功率 | 输入配对码并完成绑定的比例 | ≥ 95% | P1 实测 |
| P1 快照延迟 | 主持人操作到玩家看到更新 | P95 ≤ 5s | P1 实测 |

> 基线尚未建立，目标值为 v1.2 验收目标，实测后校准；不在本 PRD 编造历史数据。

## 3. 范围边界与功能需求

### 3.1 范围边界

**本版做（v1.2）**

- **P0**：规则与攻略查阅；单机主持（开局设置、双模式发牌、夜间引导、白天引导、自动判定、结算复盘、误操作回退一步）；个人助手（身份标记、玩家标签、信息记录、发言要点、身份攻略、独立模式、局势录入）；AI 辅助（BYOK + 云函数中转）；本地数据管理。
- **P1**：配对码联机（创建/加入/绑定/快照同步/断线恢复/解绑）；联机视图过滤；联机结算删除；复盘时间线；术语表与搜索；私人笔记；AI 输入基础过滤。
- **P2（仅预留结构）**：更多板子、人数可调、自定义板子、平台默认 AI 通道、语音播报、历史战绩、演练模式、密码学层面的身份保护。

**本版不做（明确排除）**

- 账号体系、用户昵称系统、跨对局历史查询。
- 在线匹配、陌生人房间、语音房间；仅限线下同桌、主持人控场。
- 支付、社交分享、社区内容、动画演出。
- 12 人以外的人数配置（v1.2 固定 12 人；人数可调 P2）。
- 狼队友身份云端同步（由主持人当面组织互认）。
- 密码学层面的身份保护（v1.2 用服务端视图过滤 + 前端遮罩；更强保护列 P2）。

**排除原因**

- 账号/历史/匹配会把工具变成社交产品，增加合规、成本与现场摩擦，偏离“零门槛主持”。
- 12 人固定覆盖两个目标板子；人数可调需要动态板子配置，留到 P2。
- 狼队友同步会增加权限复杂度与泄露面，线下当面互认已足够。

**P0-10 AI 上下文与输出**

- **上下文**：①我的身份；②当前局势（轮次、存活编号、公开事件；独立模式手动录入，P1 联机自动填充）；③玩家标签与信息记录；④发言要点；⑤自由描述框。
- **输出**：①信息整理；②可疑对象与依据；③下一步建议；固定显示“AI 分析仅供参考，可能出错，请自行判断”。
- **依据标注**：输出中标注“基于你标记的 X 标签 / Y 发言”，P0。
- **失败**：Key 无效/额度不足/超时给出友好文案，不阻断其他功能。
- **隐私**：请求前提示上下文将发往玩家自配的第三方模型；Key 不落库、不写日志。

### 3.3 用户故事与场景

**场景 A：新手主持一场单机面杀（核心，P0）**

小李被朋友推举当“上帝”，从没玩过。他打开小程序 → 选“预女猎守” → 选“线下逐步确认”发牌 → 按屏幕逐个确认 1–12 号身份 → 点“天黑请闭眼” → 每晚按提示唤醒守卫/预言家/狼人/女巫并记录 → 天亮后按提示完成警长竞选、死讯、发言、投票 → 系统自动判定胜负 → 结算揭晓身份。全程不需要理解规则，断网也能完成。

**场景 B：玩家独立记录 + AI 整理（P0）**

小王是 5 号预言家，不想配对。他在个人助手里选身份“预言家”，录入轮次、存活玩家和公开事件，给每位玩家打标签、记发言要点。点“AI 整理”后，系统把身份、局势、标签、要点组装后经云函数发给小王自配的模型，返回“信息整理 / 可疑对象与依据 / 下一步建议”，并提示 AI 可能出错。

**场景 C：部分玩家联机（P1）**

小李仍用同一台手机主持；愿意配对的玩家扫码加入并绑定编号，收到仅自己的身份和公开进度；不愿加入的玩家继续用纸质/口述方式。联机失败不影响主持流程。

**场景 D：临场查规则（P0）**

玩家对“同守同救”有争议，打开规则查阅 → 搜索/进入流程规则 → 查看判定说明。

**场景 E：联机结算（P1）**

主持人结算后，云端房间生成最终快照并揭晓全部身份；玩家看到结果；主持人点“结束房间”后云端数据删除。

### 3.5 关键流程与状态机

P0 主流程：

```text
首页 → 规则查阅 / 主持 / 我的助手
主持：SETUP → DEAL → NIGHT → [SHERIFF（首日）] → DAWN → SPEECH → VOTE → SETTLE → CHECK_WIN
      → 未结束 → NIGHT …
      → 结束 → RESULT → 清除本局 / 再来一局
```

P1 联机：`SETUP` 内增加 `PAIR`（可选），之后 `DEAL` 时下发本人身份；每阶段结束生成快照。

详细状态与中断见[附录 E](#附录-e-状态机)。

### 5.2 本地数据

| 键（建议） | 内容 | 保留 |
| --- | --- | --- |
| `rules_content` | 板子/角色/流程（术语 P1） | 随版本更新，只读 |
| `game_local` | 当前对局状态（主持端） | 结算后清除；结算前退出可恢复 |
| `assistant_record` | 玩家个人助手记录 | 直到用户清空 |
| `ai_config` | URL/Key/模型名 | 直到用户清空；不导出 |
| `settings` | 默认板子等 | 直到用户清空 |
| `room_token`（P1） | 房间令牌 | 结算/解散后清除 |

> Key 存储：小程序无系统级安全存储，PRD 不承诺“加密即安全”；要求不写入日志、不上传持久化、提供清空入口。若后续需要更强保护，列 P2。

### 5.3 云端数据（P1 + AI 中转）

| 数据 | 内容 | 生命周期 |
| --- | --- | --- |
| `ai_relay` | 无持久化；请求在内存中转发 | 请求结束即释放；不落库、不写日志 |
| `room`（P1） | 配对码、板子、阶段、绑定 | 创建至结算/解散 |
| `snapshot`（P1） | 公开快照 + 按角色过滤的私有视图 | 每阶段覆盖；结算/解散删除 |
| `view_acl`（P1） | 视图生成规则（代码内） | 随版本；不单独存业务数据 |

> “结算即删”指业务数据逻辑删除并停止可读；云开发备份/日志的物理留存按平台策略清理，需在隐私政策中说明。

### 5.4 数据所有权与隐私

- 玩家个人记录归玩家，仅本机；主持人不读取。
- 对局数据归主持人；结算/解散后删除；玩家可在自己设备清空本地记录。
- AI 上下文含身份/标签/发言要点，属敏感信息；请求前提示数据将发往玩家自配的第三方模型；不内置默认模型。
- 不收集真实姓名、手机号、位置；昵称为可选，提示勿填真实信息。
- 隐私政策与用户协议在上线前提供；P1 使用 openid 作为房间身份锚点。

### 5.5 一致性与幂等

- **P0**：主持端本机状态为唯一源；每步落本地，支持退出恢复。
- **P1**：主持端为写入方；快照按阶段覆盖；玩家端最终一致；加入/绑定/结算接口需幂等键，重复提交返回同一结果。
- **AI**：请求无业务幂等要求；超时/重试由玩家手动触发，避免重复扣费。

## 6. 接口与协议需求

### 6.1 AI 中转（P0）

| 项 | 要求 |
| --- | --- |
| 业务能力 | 接收玩家端组装的 messages，向玩家配置的 Chat Completions 端点转发，返回内容 |
| 权限 | 仅小程序内登录用户（openid）可调用；按 openid 限频（示例 10 次/分钟，具体值步骤 3 定） |
| 关键输入 | baseUrl、apiKey、model、messages、temperature/maxTokens（可选） |
| 关键输出 | ok、content、usage（可选）、errorCode、errorMessage（脱敏） |
| 业务错误 | KEY_INVALID、QUOTA、TIMEOUT、NETWORK、UPSTREAM_4XX/5XX、RATE_LIMITED、URL_NOT_ALLOWED |
| 时效 | 连接 30s、总 60s；超时返回 TIMEOUT |
| 安全 | 仅 https；解析域名后拒绝私网/链路本地/元数据地址；不跟随到私网的重定向；响应 ≤1MB；不打印请求体/Key |
| 失败影响 | 仅 AI 功能失败，不影响主持/助手/规则查阅 |

### 6.2 联机房间（P1）

| 能力 | 权限 | 关键输入/输出 | 时效/幂等 |
| --- | --- | --- | --- |
| 创建房间 | 主持人 openid | 板子、12 人 → 6 位配对码（10 分钟加入有效） | 幂等：同一 openid 未结算房间复用 |
| 加入/绑定 | 玩家 openid | 配对码、编号 → 申请状态 | 一号一绑；按 openid/IP 限频；重复申请返回当前状态 |
| 主持人确认 | 主持人 openid | 编号、申请 openid → 绑定成功 | 幂等 |
| 解绑/重置 | 主持人 openid | 编号 → 解绑 | 幂等 |
| 生成快照 | 主持人 openid | 阶段、公开事件、私有信息 → 快照 | 每阶段覆盖；重复生成同阶段覆盖 |
| 读取视图 | 绑定玩家 openid | 房间、编号 → 该玩家可见视图 | 5s 轮询；越权返回空/拒绝 |
| 结算/解散 | 主持人 openid | 结果 → 删除房间与快照 | 幂等；删除后不可恢复 |

> PRD 只定义业务能力与权限，不规定 HTTP 方法/路径/完整 Schema；具体契约在步骤 3 的 `api-contract` 中定稿。

### 6.3 第三方集成

| 集成 | 用途 | 方向 | 前提 | 失败影响 |
| --- | --- | --- | --- | --- |
| 玩家自配 AI（Chat Completions 兼容） | AI 整理 | 云函数 → 第三方 → 云函数 | 玩家提供 URL/Key/模型；服务可达；协议兼容 | AI 功能失败；主持/记录不受影响 |
| 微信云开发 | 云函数、P1 数据库 | 小程序 ↔ 云 | 开通云开发环境 | P0 不受影响（除 AI）；P1 联机不可用 |

### 6.4 不适用说明

- 无账号体系、无支付、无社交分享、无消息订阅；不调用微信用户信息接口。
- 无对外公开 API；云函数仅小程序内调用。

## 7. 交互与体验需求

### 7.1 信息架构

```text
首页
├─ 规则与攻略（板子/角色/流程；术语/搜索 P1）
├─ 我来主持（单机；P1 可选生成配对码）
├─ 我的助手（身份/标签/信息/发言要点/攻略/局势/AI）
└─ 设置（默认板子、清空记录、隐私说明）
```

### 7.2 关键交互流程

**主持**

1. 选板子 → 确认 12 人编号（可选昵称）→ 选发牌模式 → 设置项 → 开始。
2. 发牌：接力查看（遮罩→查看→回遮罩）或线下逐步确认（逐个显示→主持人确认）。
3. 夜晚：按顺序卡片推进；每步一个大按钮 + 编号选择；私密信息默认遮罩。
4. 首日天亮：警长竞选（报名/发言/退水/投票/平票 PK/当选或流失）。
5. 竞选结束：公布死讯 → 遗言 → 夜间技能（猎人开枪/警徽流转）→ 发言 → 投票 → 放逐后技能（白痴翻牌/猎人开枪）→ 胜负判定。
6. 结算：胜负原因 → 揭晓身份 → 关键事件 → 再来一局/返回。

**助手**

- 身份卡（联机下发或自选）→ 玩家列表（1–12）→ 标签/信息/发言要点 → 局势面板（轮次/存活/公开事件）→ AI 整理。

**P1 联机（可选）**

- 主持人生成配对码 → 玩家扫码/输码 → 选编号（二维码可携带编号，自动带入）→ 主持人逐个或批量确认 → 收到本人身份与公开快照。

**再来一局**

- 保留玩家编号，清空对局状态；P1 重新生成配对码，玩家按新码重新加入。

### 7.3 UI 风格方向

- **基调**：线下场景、昏暗环境优先；默认深色高对比，关键按钮大而明确；避免游戏化装饰与长动画。
- **主持端**：单列步骤卡片，一屏只做一件事；顶部固定“当前阶段/轮次”；底部主按钮；危险操作（自爆/结算）二次确认。
- **玩家端**：身份卡 + 玩家列表双区；私密内容默认遮罩，点击查看；标签用短 chips，发言要点按轮次折叠。
- **颜色语义**：好人/狼人/第三方仅用于身份揭示与结算，不在公共界面泄露；操作成功/失败用文字 + 颜色双重提示。
- **视觉细节**：字体、间距、组件库在步骤 5A 定稿；本 PRD 只确定方向。

### 7.4 状态要求

| 场景 | 加载 | 空态 | 成功 | 失败 | 无权限 | 重复提交 |
| --- | --- | --- | --- | --- | --- | --- |
| 规则查阅 | 本地读取，无需 loading | “暂无内容”（理论不出现） | 正常展示 | 读取失败提示重试 | 不适用 | 不适用 |
| 发牌 | 无 | 未开局提示 | 身份卡 | 本地存储失败提示 | 非当前玩家遮罩 | 防重复点击 |
| 夜间/白天 | 无 | 未到阶段提示 | 记录并进入下一步 | 校验失败提示（如连守） | 私密信息遮罩 | 防重复提交 |
| AI | loading + 取消 | 未配置 Key 引导 | 三段以上内容 + 依据 | 错误码文案 + 重试 | Key 无效提示 | 请求中禁用按钮 |
| P1 联机 | 连接中 | 未加入提示 | 快照更新 | 断线提示 + 重连 | 未绑定/越权提示 | 幂等 |
| 结算 | 无 | 未结算提示 | 胜负 + 身份 | 数据缺失提示 | 不适用 | 防重复结算 |

### 7.5 文案与可访问性

- 大白话、动词短句；首次出现的术语给一句解释；不使用“上帝视角/屠边”等术语而不解释。
- 按钮文案明确动作（“1 号已确认”而非“下一步”）。
- 触控 ≥44px；对比度 ≥4.5:1；支持系统字体放大；关键信息不只靠颜色区分。

### 7.6 兼容性

- 近两年主流微信版本；iOS/Android 主流机型；基础库最低版本步骤 3 定。
- 屏幕适配：小屏（iPhone SE 级）到大屏；横屏不强制支持。
- 深色/浅色：默认深色；跟随系统可作为 P2 优化。

## 8. 约束、依赖与风险

### 8.1 约束

- 微信原生小程序（WXML/WXSS/JS）+ 微信云开发；不引入跨端框架。
- 12 人固定；两个板子；屠边。
- 无账号体系；openid 仅用于 P1 与 AI 限频。
- P0 不依赖云数据库/实时推送；云开发仅用于 AI 中转与 P1。
- BYOK：不内置模型、不代管 Key。
- 规则以附录 A 为唯一口径；规则源文档只作资料。

### 8.2 依赖

- 微信开发者工具与云开发环境（需开通，额度/计费待确认）。
- 玩家自备的 Chat Completions 兼容服务。
- 规则内容与攻略内容的编写（规则源不含完整攻略）。

### 8.3 风险

| 风险 | 触发 | 影响 | 应对 |
| --- | --- | --- | --- |
| 规则口径差异 | 不同圈子约定不同 | 判定争议 | 附录 A 唯一口径 + 开局设置项 + “以开局约定为准” |
| 新手现场秩序 | 12 人发言/投票混乱 | 流程卡住 | 步骤卡 + 兜底话术 + 主持人可手动跳过/回退 |
| AI 输出错误 | 上下文不足/模型幻觉 | 误导玩家 | 边界提示 + 依据标注 + 定位为“整理”而非结论 |
| BYOK 安全 | Key 泄露/滥用 | 玩家损失 | 不落库/不日志/HTTPS/限频/SSRF 防护 |
| 云开发额度 | 免费额度不足/并发超限 | P1/AI 不可用 | P0 不依赖；额度监控；超限提示；必要时升级 |
| 合规/类目 | 小程序审核/游戏类目/AI 标识 | 无法上线 | 上线前专项确认；按工具类申报；AI 内容标识与提示 |
| 内容生产 | 攻略/易错点缺失 | 产品价值不足 | 单列内容任务；先覆盖两板子核心角色 |
| P1 联机可靠性 | 网络/设备/版本差异 | 玩家看不到进度 | P1 可选；主持端本地优先；快照轮询；失败话术 |
| 12 人实测成本 | 难凑齐 12 人 | 验收慢 | 用 P2 演练模式或分批走查；AC-1 用 12 人一次正式验收 |

## 9. 待确认项

### 9.1 假设与前提

## 附录 E 状态机

```text
SETUP ──(P1: PAIR)──> DEAL ──> NIGHT ──> [SHERIFF（首日）] ──> DAWN ──> SPEECH ──> VOTE ──> SETTLE ──> CHECK_WIN
   ^                                                                                                      │
   │                                                                                              未结束 ─┘
   │                                                                                                      │
   └────────────────────────────── 下一夜 <───────────────────────────────────────────────────────────────┘
                                                                                                          │
                                                                                                     结束 → RESULT
```

| 状态 | 进入条件 | 主要动作 | 退出 |
| --- | --- | --- | --- |
| SETUP | 首页点“我来主持” | 选板子、编号、发牌模式、设置 | 开始 → DEAL |
| PAIR（P1） | 主持人选择生成配对码 | 玩家加入/绑定/确认 | 发牌 → DEAL |
| DEAL | 设置完成 | 接力查看/逐步确认；记录编号→身份 | 全部完成 → NIGHT |
| NIGHT | 天黑 | 按顺序记录守护/刀/查验/用药 | 完成 → SHERIFF（首日）或 DAWN |
| SHERIFF | 首日且开启竞选 | 报名/发言/退水/投票/平票 PK/自爆吞警徽 | 当选/流失 → DAWN |
| DAWN | 天亮（首日竞选后） | 公布死讯、猎人开枪、警徽流转、遗言 | → SPEECH |
| SPEECH | 死讯/遗言完成 | 按顺序发言；可自爆 | → VOTE 或 NIGHT（自爆） |
| VOTE | 发言完成 | 录入投票/弃票；平票 PK；放逐 | → SETTLE |
| SETTLE | 投票结束 | 白痴翻牌、猎人开枪、警徽流转、胜负检查 | 未结束 → NIGHT；结束 → RESULT |
| RESULT | 胜负确定 | 揭晓身份、复盘、清除/再来一局 | 首页/新局 |

**中断规则**

- **自爆**（竞选/发言）：中止当前状态 → 直接 NIGHT；竞选自爆吞警徽；白狼王可带人；被带走的警长按警长死亡处理警徽。
- **警长死亡**（夜间/白天）：在 DAWN/SETTLE 进入警徽流转（交警徽/撕警徽）。
- **猎人被刀**：在 DAWN 开枪；**被放逐**：在 SETTLE 开枪；**被毒/殉情/白狼王带走**：不开枪。
- **白痴被放逐**：在 SETTLE 翻牌免死、失去投票权、不再成为放逐目标；不进入死亡结算。
- **胜负检查**：DAWN 死亡结算后、SETTLE 技能结算后各一次。
