## 2. 项目概述

### 2.1 背景与问题

狼人杀是强流程、强信息的社交推理游戏，线下组局存在三个典型痛点：

1. **主持门槛高**：面杀需要一位懂规则、能记住夜间顺序、会判定胜负的“上帝”。新手不会主持，导致组局困难。
2. **规则记忆负担**：板子、角色技能、行动顺序、冲突判定（如同守同救）容易记错，争议频发。
3. **玩家缺乏私人辅助**：玩家需在不暴露身份的前提下查看技能提示、记录场上信息、获得策略提示；线下又难以把这些信息汇总给每个玩家。

### 2.2 产品定位

面向**线下狼人杀场景**的移动端 Web 应用：用一台手机打开网页即可让**完全不会玩的人**按引导主持完整对局并自动给出结果；每位玩家可用自己的手机打开同一站点，记录身份、标签与发言要点，获得 AI 整理建议，且**只看到自己该看的信息**。

v1.3.2 定位：**零门槛主持人（P0）+ 私人对局助手（P0）**；**配对码联机为下一迭代 P1，不阻塞单机主持**。**手机竖屏是主场景，桌面/平板仅兼容，不做桌面专属布局。** 发牌支持两种身份来源：系统随机（模式 A/B）与实体牌录入（模式 C，系统只主持）。

### 2.3 目标用户

| 用户 | 特征 | 核心诉求 | 优先级 |
| --- | --- | --- | --- |
| **新手主持人** | 不会玩狼人杀，被推举主持 | 一步步照做完成整局，不判断、不记忆、不出错 | P0 |
| **独立玩家** | 只想自己记录，不加入房间 | 标记身份、记标签/发言，数据留本机 | P0 |
| **进阶玩家** | 追求策略提升 | 用标签/发言要点沉淀信息，让 AI 帮忙整理 | P0 |
| **联机玩家** | 每人一部手机，线下同桌 | 扫码/打开链接即加入，自动拿到身份与公开进度 | P1 |

### 2.4 核心价值

- **零门槛主持**：把“懂规则”转化为“照着点”，主持人无需先验知识。
- **移动端优先**：主流 1080p 手机 + 5G/Wi-Fi 为主；竖屏单手可操作，主按钮在拇指区；适配安全区、输入法与弱网降级；主持端防熄屏。
- **本地优先**：P0 全部主持流程与个人记录在浏览器本地完成；页面已加载后断网可继续；网络只用于 AI（可选）与 P1 联机。
- **自动裁定**：胜负、冲突、平票由系统判定，减少争议。
- **信息沉淀 + AI 整理**：标签与发言要点成为 AI 上下文；AI 输出“整理/可疑/建议/依据”，不冒充结论。
- **下一迭代联机协同（P1）**：配对码加入、WebSocket 实时同步、按角色过滤视图；不加入也能玩。
- **无安装门槛**：浏览器打开即用，不经过应用商店/小程序审核；可分享链接/二维码。

### 2.5 成功指标

| 指标 | 统计口径 | 目标值 | 观察方式 |
| --- | --- | --- | --- |
| 新手主持完成率 | 首次使用的主持人完成一整局（进入结算）的比例 | ≥ 80% | 5–10 名新手实测 |
| 对局流程完成率 | 开局后进入结算的比例 | ≥ 90% | 实测记录 |
| 开局设置耗时 | 从进入主持到发牌完成 | ≤ 3 分钟 | 实测计时 |
| 规则判定错误 | 同守同救、限一瓶、连守、1.5 票、平票等用例 | 0 错误 | 规则测试用例 |
| AI 请求成功率 | 有效 Key 下返回三段以上内容的比例 | ≥ 90% | 后端日志（脱敏） |
| P1 配对成功率 | 输入配对码并完成绑定的比例 | ≥ 95% | P1 实测 |
| P1 同步延迟 | 主持人操作到玩家看到更新 | WebSocket ≤2s；轮询降级 ≤5s | P1 实测 |

> 基线尚未建立；P0 指标为 v1.3.2 验收目标，P1 指标为下一迭代目标，实测后校准；不在本 PRD 编造历史数据。

## 3. 范围边界与功能需求

### 3.1 范围边界

**本版做（v1.3.2，P0 必须交付）**

- **P0**：规则与攻略查阅；单机主持（开局设置、三种发牌模式（接力查看/线下逐步确认/实体牌录入）、夜间引导、白天引导、自动判定、结算复盘、误操作回退一步、屏幕常亮）；个人助手（身份标记、玩家标签、信息记录、发言要点、身份攻略、独立模式、局势录入）；AI 辅助（BYOK + 后端中转）；本地数据管理；移动端优先适配（1080p/DPR 2–3、视口/安全区/单手/触控/性能）。

**下一迭代（v1.4 规划，不进入 v1.3.2 验收）**

- **P1**：配对码联机（创建/加入/绑定/WebSocket 同步/断线恢复/解绑/主持人恢复）；联机视图过滤；联机结算删除；复盘时间线；术语表与搜索；私人笔记；AI 输入基础过滤；PWA 离线壳。

**后续（P2）**

- 更多板子、人数可调、自定义板子、平台默认 AI 通道、语音播报、历史战绩、演练模式、密码学层面的身份保护。

**优先级定义**

- **P0**：v1.3.2 必须交付；缺失则产品不成立，阻塞验收。
- **P1**：下一迭代交付；不阻塞 v1.3.2 P0 验收，指标与 AC 在 P1 交付时生效。
- **P2**：后续迭代，仅预留结构。

**本版不做（明确排除）**

- 微信小程序、公众号 H5 套壳、原生 App；仅做标准 Web 页面。
- 账号体系、用户昵称系统、跨对局历史查询。
- 在线匹配、陌生人房间、语音房间；仅限线下同桌、主持人控场。
- 支付、社交分享、社区内容、动画演出。
- 12 人以外的人数配置（v1.3.2 固定 12 人；人数可调 P2）。
- 狼队友身份服务端同步（由主持人当面组织互认）。
- 密码学层面的身份保护（v1.3.2 用服务端视图过滤 + 前端遮罩；更强保护列 P2）。

**排除原因**

- 小程序审核、类目、合法域名等限制不适合快速迭代；Web 可直接部署、分享链接、扫码打开。
- 账号/历史/匹配会把工具变成社交产品，增加合规、成本与现场摩擦，偏离“零门槛主持”。
- 12 人固定覆盖两个目标板子；人数可调需要动态板子配置，留到 P2。
- 狼队友同步会增加权限复杂度与泄露面，线下当面互认已足够。

**P0-10 AI 上下文与输出**

- **上下文**：①我的身份；②当前局势（轮次、存活编号、公开事件；独立模式手动录入，P1 联机自动填充）；③玩家标签与信息记录；④发言要点；⑤自由描述框。
- **输出**：①信息整理；②可疑对象与依据；③下一步建议；固定显示“AI 分析仅供参考，可能出错，请自行判断”。
- **依据标注**：输出中标注“基于你标记的 X 标签 / Y 发言”，P0。
- **失败**：Key 无效/额度不足/超时给出友好文案，不阻断其他功能。
- **输出安全**：AI 输出按纯文本/安全 Markdown 渲染；出现不当内容提示重试；内容安全过滤列 P1-7。
- **隐私**：请求前提示上下文将发往玩家自配的第三方模型；Key 默认不持久化、不落库、不写日志。

### 3.3 用户故事与场景

**场景 A：新手主持一场单机面杀（核心，P0）**

小李被朋友推举当“上帝”，从没玩过。他用手机浏览器打开站点（或扫桌面二维码）→ 选“预女猎守” → 选“线下逐步确认”发牌 → 按屏幕逐个确认 1–12 号身份 → 点“天黑请闭眼” → 每晚按提示唤醒守卫/预言家/狼人/女巫并记录 → 天亮后按提示完成警长竞选、死讯、发言、投票 → 系统自动判定胜负 → 结算揭晓身份。全程不需要理解规则；页面已加载后即使断网也能继续。

**场景 B：玩家独立记录 + AI 整理（P0）**

小王是 5 号预言家，不想加入房间。他在个人助手里选身份“预言家”，录入轮次、存活玩家和公开事件，给每位玩家打标签、记发言要点。点“AI 整理”后，系统把身份、局势、标签、要点组装后经后端转发给小王自配的模型，返回“信息整理 / 可疑对象与依据 / 下一步建议”，并提示 AI 可能出错。

**场景 C：部分玩家联机（下一迭代 P1）**

小李仍用同一台手机主持；愿意联机的玩家扫主持人屏幕上的二维码，打开加入页并绑定编号，收到仅自己的身份和公开进度；不愿加入的玩家继续用纸质/口述方式。联机失败不影响主持流程。

**场景 D：临场查规则（P0）**

玩家对“同守同救”有争议，打开规则查阅 → 搜索/进入流程规则 → 查看判定说明。

**场景 E：联机结算（下一迭代 P1）**

主持人结算后，服务端生成最终快照并揭晓全部身份；玩家看到结果；主持人点“结束房间”后服务端房间与快照删除。

**场景 F：实体牌开局，系统主持（P0）**

老王一群人习惯用自己的实体身份牌。按板子发完牌后，主持人打开站点选“实体牌录入”，按 1→12 把身份录入系统（角色剩余数量实时校验），录完点“天黑请闭眼”。后续夜间唤醒、白天流程、自动判定与结算照常；玩家全程不看屏，只按主持人口播行动。

#### 3.7.2 三种发牌模式

模式 A/B 的身份由系统随机生成；模式 C 的身份由主持人按实体牌手动选择。三种模式均生成编号→身份映射，后续夜间/白天与判定一致。

**模式 A：接力查看**

| 步骤 | 界面行为 | 说明 |
| --- | --- | --- |
| 1 | 全屏遮罩：“请把手机交给 1 号玩家，其他人请勿观看” | 防止旁人看到 |
| 2 | 玩家点击“查看我的身份” | 显示身份名、一句话技能、阵营色 |
| 3 | 玩家点击“我已记住，交给下一位” | 回到遮罩 |
| 4 | 重复至 12 号 | 记录编号→身份；完成提示 |

**模式 B：线下逐步确认**

| 步骤 | 界面行为 | 说明 |
| --- | --- | --- |
| 1 | 主持人把手机朝向 1 号，默认显示“请 1 号确认身份”遮罩 | 不直接显示身份 |
| 2 | 主持人点击“显示身份”（二次操作） | 显示身份牌；提示遮挡 |
| 3 | 玩家确认后，主持人点“1 号已确认” | 记录并进入下一位 |
| 4 | 重复至 12 号 | 完成提示进入夜晚 |

**模式 C：实体牌录入（线下发牌，系统主持）**

| 步骤 | 界面行为 | 说明 |
| --- | --- | --- |
| 1 | 开局设置选“实体牌录入”，确认板子与 12 人编号 | 实体牌由主持人按板子线下发放；系统不生成身份 |
| 2 | 发牌页显示“请为 X 号手动选择身份”与角色池；每个角色显示剩余数量 | 只显示当前号；余量为 0 的角色不可选 |
| 3 | 主持人对照实体牌点选身份，系统记录并自动进入下一号 | 已选明细默认不展示；可“撤销上一位”纠正 |
| 4 | 12 号选完且角色构成与板子完全一致 | 完成发牌，进入夜晚；未选满或不一致不可进入 |
| 5 | 需要复核时点“核对已录（防窥）” | 二次确认后显示已录身份，提示遮挡屏幕 |

- 玩家全程不看主持屏；私密信息暴露面不高于主持人持机的模式 B。
- 自动判定使用录入映射：夜间唤醒顺序、女巫用药、守卫连守、猎人/白狼王技能、屠边胜负与结算揭晓均不受影响。

- 三种模式都支持 P1 联机：模式 A/B 在发牌完成后下发本人身份，模式 B 在主持人确认时下发；模式 C 在录入完成后按映射下发本人身份（P1 下一迭代）。
- 主持人设备是“上帝”，可见全局身份；查验/被刀等私密信息按附录 C 下发。

| 猎人/白痴 | “猎人/白痴请闭眼” | 无夜间操作 | 结算时判定开枪/翻牌 | 无 | 被毒/被白狼王带走不开枪 |
| 夜晚结束 | “天亮了，请睁眼” | 进入天亮 | 计算死亡/平安夜；同步公开信息 | 死讯公开 | 同守同救目标死亡 |

- 夜间顺序按附录 A：预女猎守“守卫→预言家→狼人→女巫”；预女猎白“预言家→狼人→女巫”。
- 每步一张大卡片：角色名 + 口播 + 大按钮 + 1–12 编号网格；私密信息默认遮罩。

#### 3.7.4 白天流程

1. **首日警长竞选**：报名 → 依次发言 → 退水 → 警下投票 → 得票最多者当选；平票 PK 复投，再平本局无警长；首夜死者系统内部排除；警上无投票权；竞选自爆吞警徽。
2. **死讯与遗言**：公布“昨夜 X 号出局”或“平安夜”；首夜/白天死亡有遗言，其余夜晚无；猎人被刀在此时开枪；警长死亡在此或放逐后交警徽/撕警徽。
3. **发言**：警长指定顺序，或死左/死右；支持自爆打断。
4. **投票放逐**：主持人逐票录入或点选归票对象；支持弃票；平票进 PK 复投，再平本轮无人出局；警长票 1.5；白痴翻牌后无票。
5. **放逐后结算**：白痴翻牌免死；猎人被放逐开枪；警徽流转；随后胜负检查。
6. **自爆**：竞选/发言阶段可自爆；中止当前流程 → 白狼王带人（如有）→ 警徽处理（如竞选）→ 胜负检查 → 入夜或结算。
7. **胜负**：屠边；每次夜间死亡结算后、白天技能结算后、自爆结算后检查。

#### 3.7.8 异常、回退与二次确认

- **回退一步**：主持人本机保留上一步快照；仅主持端可用；回退需二次确认；结算后不可回退。
- **二次确认**：发牌完成、投票提交、结算、自爆、解绑/重开。
- **常见拦截**：编号缺号/重号、守卫连守、女巫同夜两瓶、非法目标、重复投票、白痴无票、平票流程未完成、未发牌进入夜晚、实体牌模式未选满 12 人、角色余量不足或角色构成与板子不一致。
- **P1 回退**：主持端本地为准；回退后重新写入服务端快照（下一迭代）。
- 验收：AC-18。

### 5.2 本地数据

| 键（建议） | 内容 | 保留 |
| --- | --- | --- |
| `rules_content` | 板子/角色/流程（术语 P1） | 随版本更新，只读 |
| `game_local` | 当前对局状态（主持端） | 结算后清除；结算前刷新可恢复 |
| `assistant_record` | 玩家个人助手记录 | 直到用户清空 |
| `ai_config` | URL/模型名；Key 默认不持久化 | 直到用户清空；不导出 |

- 本地存储使用浏览器 localStorage / IndexedDB；容量与清理策略在步骤 3 定。
- **本地存储可能被浏览器清理**：关键对局每步落库；提示“游戏中不要清理浏览器数据”；PWA 离线壳为下一迭代。

### 5.3 服务端数据（P1 + AI 中转）

| 数据 | 内容 | 生命周期 |
| --- | --- | --- |
| `ai_relay` | 无持久化；请求在内存中转发 | 请求结束即释放；不落库、不写日志 |
| `room`（P1） | 配对码、板子、阶段、绑定 | 创建至结算/解散 |
| `game_state`（P1，服务端专用） | 完整对局状态（身份、夜间动作、公开事件），用于校验与生成视图 | 每阶段覆盖；仅服务端访问；结算/解散删除 |
| `snapshot`（P1） | 服务端生成的公开快照 + 按角色过滤的私有视图 | 每阶段覆盖；结算/解散删除 |
| `view_acl`（P1） | 视图生成规则（代码内） | 随版本；不单独存业务数据 |

> “结算即删”指业务数据逻辑删除并停止可读；数据库备份/日志的物理留存按运维策略清理，需在隐私政策中说明。

### 5.4 数据所有权与隐私

- 玩家个人记录归玩家，仅本机；主持人不读取。
- 对局数据归主持人；结算/解散后删除；完整对局状态仅服务端用于校验/生成视图，不下发玩家；玩家可在自己设备清空本地记录。
- AI 上下文含身份/标签/发言要点，属敏感信息；请求前提示数据将发往玩家自配的第三方模型；不内置默认模型。
- 不收集真实姓名、手机号、位置；昵称为可选，提示勿填真实信息。
- 匿名会话 ID 仅用于房间绑定与限频，不作为账号；隐私政策与用户协议在上线前提供。
- 境内服务器需 ICP 备案；具体合规项在 9.2 跟踪。

### 5.5 一致性与幂等

- **P0**：主持端本机状态为唯一源；每步落本地，支持刷新恢复。
- **P1（下一迭代）**：服务端为房间状态存储与分发方；主持端是唯一写入者；玩家端只读自己的视图；WebSocket 推送 + 轮询降级；快照带 `version`，服务端拒绝旧版本；主持端写入失败重试、重连后补写；加入/绑定/结算接口需幂等键，重复提交返回同一结果。
- **AI**：请求无业务幂等要求；超时/重试由玩家手动触发，避免重复扣费。

### 6.1 AI 中转（P0）

| 项 | 要求 |
| --- | --- |
| 业务能力 | 接收前端组装的 messages，向玩家配置的 Chat Completions 端点转发，返回内容 |
| 权限 | 仅已建立匿名会话的前端可调用；按会话/IP 限频（示例 10 次/分钟，具体值步骤 3 定） |

### 7.2 关键交互流程

**进入**

- 手机浏览器打开站点 URL，或扫描主持人屏幕上的二维码进入；无需安装、无需登录。

**主持**

0. 首次进入：3 步引导 + 浏览器能力/赛前加载提示；可跳过。
1. 选板子 → 确认 12 人编号（可选昵称）→ 选发牌模式 → 设置项 → 开始。
2. 发牌：接力查看（遮罩→查看→回遮罩）、线下逐步确认（默认遮罩→二次显示身份→主持人确认）或实体牌录入（线下发牌→按 1→12 录入身份→校验构成）。
3. 夜晚：按 3.7.3 逐角色口播/卡片推进；狼人先睁眼互认；私密信息默认遮罩。
4. 首日天亮：警长竞选（报名/发言/退水/投票/平票 PK/当选或流失）。
5. 竞选结束：公布死讯 → 遗言 → 夜间技能（猎人开枪/警徽流转）→ 发言 → 投票 → 放逐后技能（白痴翻牌/猎人开枪）→ 胜负判定。
6. 结算：胜负原因 → 揭晓身份 → 关键事件 → 再来一局/返回。

**助手**

- 身份卡（联机下发或自选）→ 玩家列表（1–12）→ 标签/信息/发言要点 → 局势面板（轮次/存活/公开事件）→ AI 整理。

**P1 联机（可选）**

- 主持人生成配对码/二维码 → 玩家扫码或输码 → 选编号 → 主持人逐个或批量确认 → 收到本人身份与公开快照；WebSocket 实时更新，断线自动重连，失败时 5s 轮询降级。加入页提示“同一浏览器完成绑定”；P1 为下一迭代。

**再来一局**

- 保留玩家编号，清空对局状态；P1 重新生成配对码，玩家按新码重新加入。

### 7.3 UI 风格方向

- **基调**：线下场景、昏暗环境优先；默认深色高对比，关键按钮大而明确。
- **视觉方向（2026-11-25 重设计）**：月蚀俱乐部 / Moonlit Parlor —— 暗色月夜、金色与血红点缀、宋体大标题、塔罗牌式身份卡、玩家席位圆章；氛围装饰与短动画只服务于气氛，不阻塞操作，不做长演出。
- **字体与动效**：标题用衬线/宋体形成性格，正文用系统无衬线保证可读；页面入场、月晕/雾气、按钮高光克制使用，尊重 `prefers-reduced-motion`；不引入外部字体/图片，保持离线可打开。
- **移动端布局**：竖屏优先；主操作固定在底部拇指区；单列卡片，不横向滚动；适配刘海/底部 Home 条安全区。
- **大厅与导航（2026-11-25）**：首页采用“游戏大厅”结构——品牌 Hero、今晚牌桌、流程仪式条与入口卡；移动端主导航采用底部 Tab（首页/主持/助手/规则）；对局进行中隐藏 Tab，避免误触，底部由主操作坞接管；PC 保持双栏，不展示底部 Tab。
- **流程可视化与角色形象（2026-11-25）**：对局内顶部固定一阶流程条（设置/发牌/夜晚/白天/结算），白天再显示二阶子步骤（竞选/死讯/发言/投票；关闭首日竞选或第 2 天起自动收起“竞选”）；发牌与夜间以当前座位/角色为视觉焦点；8 个角色使用同一套线稿头像（好人金色、狼人血红），用于规则图鉴、身份揭示、夜间引导与结算。头像仅作识别与氛围，不改变信息可见性。
- **触控**：所有交互可点按；不依赖 hover/右键；1–12 号用大网格或底部抽屉选择，避免小下拉；危险操作二次确认。
- **输入**：输入框 ≥16px 防 iOS 自动缩放；键盘弹出时避让；长文本可折叠。
- **主持端**：单列步骤卡片，一屏只做一件事；顶部固定“当前阶段/轮次”；底部主按钮；游戏进行中刷新/离开提示；每步落本地。
- **玩家端**：身份卡 + 玩家列表双区；私密内容默认遮罩，点击查看；标签用短 chips，发言要点按轮次折叠。
- **颜色语义**：好人/狼人/第三方仅用于身份揭示与结算，不在公共界面泄露；操作成功/失败用文字 + 颜色双重提示。
- **视觉细节**：字体、间距、组件库在步骤 5A 定稿；本 PRD 只确定方向。

### 7.5 文案与可访问性

- 大白话、动词短句；首次出现的术语给一句解释；不使用“上帝视角/屠边”等术语而不解释。
- 按钮文案明确动作（“1 号已确认”而非“下一步”）。
- 触控 ≥44px；对比度 ≥4.5:1；支持系统字体放大；关键信息不只靠颜色区分。

### 7.6 兼容性

- **主场景**：主流 1080p 手机，CSS 竖屏 360–440px（主设计 360；320 兼容地板；DPR 2.5–3）；iPhone 390/393/430/440、Android 360/384/412；320px/旧机仅兼容抽查；桌面/平板仅兼容，不做专属布局；横屏不强制支持。
- **浏览器**：Chrome/Safari 主测；UC/QQ 抽查；微信内置浏览器（X5/XWeb）单独真机；具体版本基线步骤 3 定。
- **高清屏**：图标用 SVG，图片提供 2x/3x 或 WebP，避免 DPR 2–3 下模糊。
- **iOS**：使用 100dvh、safe-area；输入框 ≥16px 防自动缩放；键盘弹出避让。
- **微信内置浏览器**：PWA/部分能力可能不可用；关键流程保证可用，完整体验建议用系统浏览器打开。
- **网络**：5G/Wi-Fi 为主；4G/弱网降级；WebSocket 不可用时自动降级 5s 轮询；页面隐藏时暂停无谓请求。
- **深色/浅色**：默认深色；跟随系统可作为 P2 优化。

### 7.7 移动端专项优化

> 本节基线来自 2026-11 公开数据，详见附录 G。设计按 CSS 360–440px，主设计 360px，320px 为兼容地板。

**7.7.1 视口与安全区**

- `viewport-fit=cover` + `env(safe-area-inset-*)`；底部主按钮避开 Home 条/手势区。
- **1080p 是物理分辨率**：CSS 视口按 360–440px（主设计 360；320 兼容地板；DPR 2.5–3）设计，图标/图片按 DPR 2–3 准备，不要按 1080 CSS px 排版。
- 高度用 `100dvh` 而非 `100vh`，避免 iOS 地址栏/键盘导致的跳动。
- 使用 `touch-action: manipulation`，避免双击缩放与 300ms 延迟。
- 竖屏为主；不出现横向滚动；宽表改为卡片/折叠。

**7.7.2 单手与触控**

- 主操作固定在底部拇指区；顶部只放状态与返回。
- 触控 ≥44×44px；相邻按钮间距 ≥8px；危险操作二次确认。
- 正文 ≥14px，关键信息 ≥16px；一行不超过合理字数。
- 1–12 号用大网格/底部抽屉，不用小下拉或键盘输入。
- 不依赖 hover；按下/禁用/加载都有反馈；可用时给轻振动。

**7.7.3 性能预算**

- 首屏 JS（gzip）≤250KB；首屏请求 ≤15；路由/规则内容按需加载。
- 系统字体 + SVG 图标；图片提供 2x/3x 或 WebP；避免大图/大动画。
- 5G/Wi-Fi 首屏 ≤2s、可交互 ≤3s；4G ≤3s/≤5s；主流机型 60fps、中端 ≥55fps；长任务 ≤50ms。
- 120Hz 面板已占 Android 约一半，但 60fps 足够；不追求 120fps，优先稳定与省电。
- 玩家网格/列表避免不必要重渲染；AI 结果分段渲染。

**7.7.4 网络与离线**

- WebSocket 断线重连（指数退避）；失败降级 5s 轮询；页面隐藏暂停无谓请求。
- 弱网/断网提示；本地每步落库；P0 页面已加载后断网可继续；赛前先加载、游戏中不要清理浏览器数据；PWA 离线冷启动 P1。
- AI 请求 loading/取消/超时；超时 60s；不阻塞其他功能。

**7.7.5 屏幕常亮与防误触**

- 主持端开局后请求 Wake Lock；结算/退出/页面隐藏释放；页面重新可见时重新请求；不支持时提示手动关闭自动锁屏。MDN 标注 iOS Safari 18.4+；旧版/微信内走 fallback。
- 游戏进行中刷新/离开给出提示；每步已落本地，恢复后回到当前步骤。
- 发牌/投票/结算二次确认；返回键不直接清空对局。

**7.7.6 设备与浏览器矩阵**

- 主测：iPhone 390/393/430/440、Android 360/384/412（DPR 2.5–3）；320px 兼容抽查。
- 浏览器：Chrome/Safari 主测；UC/QQ 抽查；微信内置浏览器单独真机；桌面 Chrome 仅兼容检查。
- 网络：5G、Wi-Fi 为主；4G/弱网降级；断网后恢复。

**7.7.7 测试方法**

- Chrome DevTools 设备模拟 + 真机；Lighthouse 移动端（5G/4G 两档）；真机录屏测帧率。
- 每轮发版跑 AC-16/AC-17；联机另跑 P1 断线/重连。

## 8. 约束、依赖与风险

### 8.1 约束

- **Web 应用**：前端 + 后端服务；默认前后端分离（SPA + API/WebSocket），允许全栈框架；具体技术栈在步骤 3 定。
- **移动端优先**：主流 1080p 手机 + 5G/Wi-Fi 为主；CSS 竖屏 360–440px（主设计 360；320 兼容地板；DPR 2.5–3）；320px/旧机仅兼容；桌面/平板仅兼容；不做桌面专属布局；性能/触控/安全区约束见第 4 章与 7.7。
- 不使用微信小程序、公众号 H5 套壳、原生 App；不依赖应用商店/小程序审核。
- 12 人固定；两个板子；屠边。
- 无账号体系；匿名会话 + 房间令牌；会话 Cookie 为 httpOnly + Secure + SameSite。
- P0 主持/助手不依赖后端；AI 为可选网络功能；P1 依赖后端 API/WebSocket/数据库。
- BYOK：不内置模型、不代管 Key；Key 默认不持久化。
- 规则以附录 A 为唯一口径；规则源文档只作资料。
- HTTPS + 域名；境内服务器需 ICP 备案；数据库不对外暴露；Node 单进程提供静态/API/WS，不使用 Nginx/Docker；TLS 由 Node HTTPS 或云负载均衡终止。

### 8.2 依赖

- 服务器（Linux/Node 24 运行环境）、域名、HTTPS 证书（Node HTTPS 或云负载均衡）、SQLite（P1）；不使用 Nginx/Docker。
- 关系型数据库（SQLite/PostgreSQL 在步骤 3 定）。
- 玩家自备的 Chat Completions 兼容服务。
- 规则内容与攻略内容的编写（规则源不含完整攻略）。

### 8.4 部署与运行环境

- **拓扑**：浏览器 → HTTPS → Node/Fastify 单进程（`@fastify/static` 静态 + API + P1 Socket.IO）→ SQLite（P1）。不使用 Nginx/Docker。
- **TLS**：Node HTTPS 直接终止（证书由 certbot/DNS 或云证书提供），或云负载均衡/CDN 终止后回源 Node 3000；Cookie Secure、WebSocket wss、HSTS。
- **静态资源**：Fastify static 提供 `apps/web/dist`；SPA fallback；哈希资源长缓存、`index.html` 不缓存；gzip/brotli 压缩。
- **域名/备案**：境内服务器需 ICP 备案；境外服务器需评估访问延迟与合规。
- **数据库**：SQLite（P1）文件持久目录；不监听公网；定期备份；房间数据结算/解散删除。
- **进程**：Node 单进程，systemd/PM2 守护；API 与 WebSocket 同进程；单实例；水平扩展前确认粘性会话/共享状态。
- **日志**：Fastify/pino 结构化、脱敏；不记录 Key、AI 上下文全文、玩家笔记；保留期在部署文档中定。
- **CORS**：生产同源（Node 同时提供静态与 API），无需 CORS；开发用 Vite proxy。
- **证书/回滚**：监控证书到期；保留上一版静态资源与后端构建；迁移前备份；前滚修复优先。

> 2026-11-25 调整：根据用户决定不使用 Nginx/Docker；如未来需要 TLS 卸载、静态加速或多实例，再评估云负载均衡/CDN、Nginx 或容器化。
- **资源目标**：10 房间 × 13 人 ≈ 130 个 WebSocket 连接；按试运行结果调整。

## 附录 E 状态机

```text
SETUP ──(P1: PAIR)──> DEAL ──> NIGHT ──> [SHERIFF（首日）] ──> DAWN ──> SPEECH ──> VOTE ──> SETTLE ──> CHECK_WIN
   ^                                                                                                      │
   │                                                                                              未结束 ─┘
   │                                                                                                      │
   └────────────────────────────── 下一夜 <───────────────────────────────────────────────────────────────┘
                                                                                                          │
                                                                                                     结束 → RESULT
```

> 自爆中断：SHERIFF/SPEECH → SELF_EXPLODE → CHECK_WIN → NIGHT/RESULT。

| 状态 | 进入条件 | 主要动作 | 退出 |
| --- | --- | --- | --- |
| SETUP | 首页点“我来主持” | 选板子、编号、发牌模式、设置 | 开始 → DEAL |
| PAIR（P1） | 主持人选择生成配对码 | 玩家加入/绑定/确认 | 发牌 → DEAL |
| DEAL | 设置完成 | 接力查看/逐步确认/实体牌录入；记录编号→身份 | 全部完成（模式 C 需构成一致）→ NIGHT |
| NIGHT | 天黑 | 按顺序记录守护/刀/查验/用药 | 完成 → SHERIFF（首日）或 DAWN |
| SHERIFF | 首日且开启竞选 | 报名/发言/退水/投票/平票 PK/自爆吞警徽 | 当选/流失 → DAWN；自爆 → SELF_EXPLODE |
| DAWN | 天亮（首日竞选后） | 公布死讯、猎人开枪、警徽流转、遗言 | → CHECK_WIN → SPEECH |
| SPEECH | 死讯/遗言完成 | 按顺序发言；可自爆 | → VOTE；自爆 → SELF_EXPLODE |
| SELF_EXPLODE | 竞选/发言自爆 | 白狼王带人、警徽处理、胜负检查 | 未结束 → NIGHT；结束 → RESULT |
| VOTE | 发言完成 | 录入投票/弃票；平票 PK；放逐 | → SETTLE |
| SETTLE | 投票结束 | 白痴翻牌、猎人开枪、警徽流转、胜负检查 | 未结束 → NIGHT；结束 → RESULT |
| RESULT | 胜负确定 | 揭晓身份、复盘、清除/再来一局 | 首页/新局 |

**中断规则**

- **自爆**（竞选/发言）：中止当前状态 → `SELF_EXPLODE` → 白狼王带人（如有）→ 警徽处理（如竞选）→ 胜负检查 → 入夜或结算。
- **警长死亡**（夜间/白天）：在 DAWN/SETTLE 进入警徽流转（交警徽/撕警徽）。
- **猎人被刀**：在 DAWN 开枪；**被放逐**：在 SETTLE 开枪；**被毒/殉情/白狼王带走**：不开枪。
- **白痴被放逐**：在 SETTLE 翻牌免死、失去投票权、不再成为放逐目标；不进入死亡结算。
- **胜负检查**：自爆结算后、DAWN 技能结算后、SETTLE 技能结算后各一次。

### G.4 调研结论

1. 设计按 CSS 360–440px，主设计 360px；390/393/412/430/440 重点回归；320px 是缩放/大字模式下的兼容地板，不能删除。
2. 资源按物理 1080p 起步、DPR 2–3 准备；图标 SVG，照片 2x/3x/WebP。
3. 5G/Wi-Fi 为主，首屏 ≤2s、可交互 ≤3s 可达成；4G/弱网保留 ≤3s/≤5s 与降级提示。
4. 60fps 是合理目标；120Hz 面板按 60fps 渲染即可。
5. 浏览器主测 Chrome/Safari，UC/QQ 抽查，微信内置浏览器单独真机验证。
6. Wake Lock 按 iOS 18.4+ 支持处理；旧版/微信内 fallback。
